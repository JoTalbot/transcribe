# Transcribe V2 — Conversation Intelligence Architecture

## Goal

Transcribe is evolving from a single-recording transcription pipeline into an evidence-backed conversation intelligence system. The pipeline keeps raw audio and deterministic transcript artifacts separate from higher-level probabilistic analysis.

## Processing layers

1. **Ingest** — register every source recording, calculate a content hash, preserve source metadata, and assign a stable `recording_id`.
2. **Normalize** — decode with FFmpeg, standardize analysis audio, detect duration, channels, sample rate, clipping and low-quality input.
3. **ASR** — Whisper/faster-whisper with word timestamps, language and segment confidence metadata.
4. **Diarization** — detect local speaker turns and create per-recording speaker embeddings.
5. **Speaker fusion** — cluster speaker occurrences across recordings. A voice cluster is not automatically a real-world identity.
6. **Entity extraction** — people, organizations, locations, products, dates, phone-like references and other domain entities.
7. **Name evidence** — detect introductions, direct address and third-party references such as `Сергей, отправь...` or `это мой брат Алексей`. Store the exact evidence span and confidence.
8. **Entity resolution** — combine names, aliases, conversation context and other evidence. Identity remains a hypothesis until sufficiently supported.
9. **Topics** — hierarchical topics plus embeddings for segments, conversations and evolving conversation threads.
10. **Intent / events / relations** — requests, offers, plans, questions, commitments, negotiations, events and explicit relationships, each linked to evidence.
11. **Conversation linking** — connect recordings into conversation threads using time, participants, entities, topic similarity and semantic references.
12. **Knowledge graph** — represent people, speaker clusters, recordings, conversations, topics, entities, events and relations as a temporal graph.
13. **Search / analytics** — hybrid lexical + vector retrieval with confidence and evidence-first explanations.

## Identity model

The system deliberately separates:

```text
recording speaker occurrence
        ↓
voice cluster
        ↓
speaker profile
        ↓
person identity hypothesis
```

A `voice_cluster` means that acoustic evidence suggests multiple occurrences may belong to one voice. It does not by itself establish the person's civil identity. `person_identity` records must contain provenance and confidence.

## Evidence model

Every extracted fact that can influence downstream reasoning should point back to source evidence:

```text
fact → evidence → recording → time range → transcript span
```

Examples include names, relationships, intents, entities, topic assignments and conversation links. This makes results auditable and allows later models to retract or downgrade weak conclusions.

## Data model

The canonical interchange format is `schemas/conversation.schema.json`. Core identifiers are stable UUID-like strings generated by the orchestrator. Raw audio is never embedded in the graph payload.

Recommended persistent tables/collections:

- `recordings`
- `speaker_occurrences`
- `voice_clusters`
- `speaker_profiles`
- `person_hypotheses`
- `conversations`
- `conversation_threads`
- `segments`
- `entities`
- `entity_mentions`
- `topics`
- `intents`
- `events`
- `relations`
- `evidence`
- `embeddings`
- `processing_jobs`

PostgreSQL + pgvector is the preferred first implementation. A dedicated graph database can be introduced later if graph workloads justify it.

## Embeddings

Maintain separate vector spaces for different retrieval tasks rather than one universal vector:

- transcript segment embedding
- conversation embedding
- topic embedding
- entity-description embedding
- speaker voice embedding

Speaker embeddings must remain isolated from text embeddings. Cross-modal similarity should be explicit and never silently substitute one modality for another.

## Confidence

Confidence is attached to individual assertions, not to an entire person or conversation. Suggested fields:

- `score`: 0..1
- `method`: deterministic/model/hybrid
- `evidence_ids`: supporting evidence
- `created_at`
- `model_version`

Conflicting evidence is retained. The system should not overwrite earlier observations merely because a later model produced a different hypothesis.

## Idempotency

Every stage is resumable:

```text
INGEST ✓
ASR ✓
DIARIZATION ✓
SPEAKER_EMBEDDING ✓
TOPICS ✗
```

A retry resumes at the first incomplete or invalid stage. Artifacts are written atomically and processing state records the model/configuration version used to create them.

## GPU strategy

The Oracle ARM Ubuntu host is the persistent orchestrator and browser worker. Heavy GPU inference can be delegated to an authenticated Google Colab session. No Google browser profile, cookies, or credentials belong in GitHub. The architecture must also support replacing Colab with another GPU worker later without changing the data model.

## Quality strategy

Quality is measured independently for ASR, diarization, speaker clustering, entity extraction, identity hypotheses, topic assignment and conversation linking. Downstream conclusions inherit provenance and uncertainty instead of presenting weak inference as fact.

## Privacy and safety

Audio, transcripts and identity hypotheses can contain highly sensitive information. Keep source data outside the Git repository, minimize retention, encrypt storage where possible, and expose only the evidence required for a specific analytical request. Do not use a voice embedding alone to claim a person's real-world identity.
